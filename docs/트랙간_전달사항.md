## 0. 한눈에 보기

```
담당자 Outlook ─(LEONA 패널)─▶ A: 케이스 생성·원문 저장 ─▶ B: 추출 ─▶ C: 검증(누락 판정)
                                                                         ├ 부족 → C: 보완 문항 → A: 보완 요청 초안(초안함) → 담당자 발송
                                                                         └ 충족 + 요율 → C: 견적서 PDF·XLSX → A: 견적서 송부 초안 → 담당자 발송
화주 회신 ─▶ A: 대상 케이스 제시 → 담당자 확인 후 병합 ─▶ B·C 자동 재실행
```

- A트랙 쪽(입구·출구·회신 연결)은 **실제 Outlook에서 끝까지 동작 확인**했습니다. 지금 비어 있는 칸은 **B 추출, C 검증·보완 문항·견적서 생성**입니다.
- 자동 발송은 없습니다. 모든 메일은 담당자가 직접 [보내기]를 누릅니다(정의서 12장).
- 메일 본문은 로컬 서버에만 저장하고 외부로 보내지 않습니다(NFR-04). B트랙 LLM도 로컬에서만 돌려야 합니다.

## 1. 공통 — 메일 표준 JSON (`MailSnapshot` v1)

애드인 패널·.eml 리더·백엔드가 모두 이 모양을 씁니다. 정의: `server/app/schemas.py` `MailSnapshot`.

| 키 | 타입 | 설명 |
|---|---|---|
| subject | str | 제목 |
| from | {name, email} | 보낸 사람 |
| to, cc | [{name, email}] | 받는 사람·참조 |
| receivedAt | ISO 8601 / null | 수신 시각 (UTC) |
| bodyText | str | 본문 텍스트. **인용문(이전 메일)이 그대로 들어 있음** — 아래 2-1 참고 |
| conversationId | str / null | Outlook 대화 ID (.eml 입력에는 없음) |
| internetMessageId | str / null | Message-ID 헤더. 중복 방지(FR-105) 기준 |
| inReplyTo, references | str / [str] | 회신 식별(FR-104)용 헤더 |
| attachments | [{filename, contentType, size, sha256}] | 첨부 목록 (파일 자체는 저장소에 별도 보관) |

- **원문은 항상 보존**합니다: `server/storage/<케이스ID>/mail-NN/original.eml` (+ 첨부 파일). 파싱이 부족하면 원문 .eml을 직접 읽어도 됩니다.
- 대량 테스트용 입력: `python -m app.eml_reader samples\eml` → 같은 JSON 출력. 샘플 .eml은 `server/samples/eml/`.
- **6장 필드와 별개입니다.** MailSnapshot은 "메일 이력" 시스템 데이터이고, 6장 추출 스키마(commodity, pol, pod …)는 B트랙이 확정합니다.

## 2. B트랙(추출)에 전달

### 연결 방법
`server/app/pipeline.py`의 `Extractor` 규격을 구현해 `register(extractor=…)`로 등록합니다.

```python
class Extractor(Protocol):
    name: str
    def extract(self, session: Session, case: Case) -> dict | None: ...   # 6장 필드 JSON
```

- **언제 불리나:** 케이스 생성 직후, 화주 회신 병합 직후 (백그라운드, 담당자는 기다리지 않음).
- **60초 기준(FR-101·NFR-02):** A가 호출~완료 시간을 `elapsedMs`·`withinLimit`으로 이력에 남깁니다. 추출+검증 합쳐 60초 안에 끝나야 합니다.
- **예외가 나도 됩니다:** A가 잡아서 케이스는 유지하고 상태 `실패` + 오류 이력을 남깁니다(NFR-03). 대신 오류 메시지를 알아볼 수 있게 던져 주세요.
- `case.mails`에 원문(ORIGINAL)과 회신(REPLY)이 순서대로 있습니다. 회신이 병합되면 **전체 메일을 다시 읽어 부족분을 합쳐야** 합니다(MUST-SHIP ③).

### 2-1. 실제 검증에서 발견한 입력 특성 (추출할 때 주의)
1. **본문에 인용문이 포함됩니다.** Outlook 회신은 `________________ / 보낸 사람: … / 보낸 날짜: …` 아래에, Gmail 회신은 `2026년 9월 29일 (화) 오전 11:46, 박재석 <…>님이 작성:` 아래 `> `로 시작하는 줄에 이전 메일이 들어 있습니다. **인용문 분리는 역할분담서·WBS 3.5 기준 B트랙 몫**입니다. A는 원문을 자르지 않고 넘깁니다(서명이 잘려 나가면 FR-208 연락처 추출이 안 되기 때문).
2. **Outlook에서 쓴 번호 목록은 번호와 내용이 줄로 갈라집니다.** 예: `  1.\r\n픽업지: 경기도 남양주시`. Gmail 텍스트 메일은 `1. 출고 가능일: …` 한 줄로 옵니다. 두 형태를 모두 처리해야 합니다.
3. **줄바꿈은 `\r\n`** 입니다.
4. **8-2 FOB는 다품목**(`[화장품]`, `[의류]` 섹션)입니다. FR-210 수동 처리 감지 대상입니다. A는 두 섹션을 섞지 않고 원문 그대로 넘깁니다(핵심 값 22개 보존 확인).
5. **8-1 LCL 불일치:** 픽업지 '인천' vs 본문 '남양주 픽업', 박스당 0.038CBM × 10 = 0.38CBM인데 전체 0.19CBM으로 기재.
6. 화주 연락처(FR-208 contactEmail)는 헤더(`from`)와 서명에 있습니다. 추출하면 A의 초안 받는 사람을 그 값으로 바꿀 예정입니다(지금은 최초 요청 메일의 보낸 사람).

### 확인 요청
- MailSnapshot v1 키 이름·타입 그대로 써도 되는지 (바꾸려면 A와 같이 바꿔야 함)
- 추출 결과 JSON에 근거(원문 위치)·신뢰도 구조를 넣을지 — NFR-05 "판단 근거 로그"에 필요

## 3. C트랙(검증·견적)에 전달

### 3-1. 검증 연결
`pipeline.py`의 `Validator` 규격 + `register(validator=…)`.

```python
class Validator(Protocol):
    name: str
    def validate(self, session: Session, case: Case, extraction: dict | None) -> dict | None: ...
```

- 추출 직후 같은 백그라운드 작업에서 불립니다. **케이스 상태(정보부족·계산완료 등)는 C가 `case.status`에 정합니다.** C가 상태를 안 바꾸면 A가 실행 전 상태로 되돌립니다(파싱중에 멈추지 않게).
- 상태 값은 6장 caseStatus 10개만 씁니다: 수신, 파싱중, 정보부족, 보완대기, 재파싱, 계산완료, 승인대기, 발송완료, 보류, 실패.
- **A가 바꾸는 상태:** 추출 중 `파싱중`/`재파싱`, 보완 요청 발송 확인 시 `보완대기`, 견적서 송부 발송 확인 시 `발송완료`. 상태 전이 규칙의 최종 결정은 D트랙(FR-107)과 맞춰 주세요.

### 3-2. 보완 요청 문항 (FR-304·305)
- 지금은 담당자가 패널 '메일 초안' 칸에 **직접 입력**합니다(C 연결 전 임시).
- A 쪽 API: `POST /api/cases/{케이스ID}/drafts/supplement` 본문 `{"questions": ["…", "…"], "actor": "담당자 이메일"}` → 받은 문항을 **그대로** 번호 목록으로 만들고(FR-305: 임의 추가·누락 없음), 제목에 케이스 ID, 국·영문 병기(FR-510).
- **요청:** 검증 결과에 "누락 항목별 보완 문항 문장 목록"을 넣어 주세요. A가 그 목록을 패널 칸에 자동으로 채우겠습니다. 형식 제안: `validation["questions"] = ["화물 준비일(Cargo Ready Date)을 알려 주세요.", …]`

### 3-3. 견적서 파일 (FR-504·505)
- 생성한 PDF·XLSX를 **`server/storage/<케이스ID>/quotes/`** 에 두거나 `POST /api/cases/{케이스ID}/quotes`(파일 업로드)로 등록하면 됩니다. A의 [견적서 송부 초안 만들기]가 이 폴더의 PDF·XLSX를 모두 첨부합니다.
- 견적서가 없으면 A는 송부 초안을 만들지 않고 안내합니다("이 케이스에 등록된 견적서가 없어 …"). FR-501(요율 없으면 견적 안 만듦)과 같은 방향입니다.
- 파일 이름 권장: `<케이스ID>_견적서.pdf` / `.xlsx` (한글 파일명 정상 동작 확인. 단 Windows curl로 올리면 이름이 깨짐 — httpx·Swagger는 정상).
- **발주 측 양식 확인 결과 (`docs/양식/`):**
  - 세 양식 모두 **케이스 ID(LQ-…) 칸이 없습니다.** FR-102는 "화면·메일 제목·**견적서**에 동일 표기"입니다 → 표기 위치를 정해 주세요(예: Subject 줄 또는 DATE 옆).
  - **ETD/ETA, Free Time(DET/DEM) 칸도 없습니다** (FR-507 필수 표기).
  - 회사명 표기는 양식 기준 "레오나해운항공㈜ / LEONA SEA & AIR CO., LTD." — A의 메일 초안도 이 표기로 맞췄습니다(정의서의 "LEONA Shipping & Air"는 쓰지 않음).
  - xlsx 시트명 "CIF 견적서 (FCL, 20')", 비용 11행 + TOTAL(USD+KRW), DATE 셀 `=TODAY()`.
- **요율표 미수령:** 발주 측이 "샘플 요율표·부대비용 Excel 금주 내 제공"이라 했지만 아직 없습니다(`docs/client_messages.md` 회신 4항). 발주 측 질문 목록에 넣어 두었습니다.
- 지금 A 테스트에 쓴 견적서는 **발주 측 예시 파일 그대로**(LCL/FOB 예시 PDF + 빈 양식 XLSX)라 금액·수량이 케이스와 맞지 않습니다.

## 4. D트랙(콘솔·검수)에 참고
- 케이스 목록·상세·이력 API: `GET /api/cases`, `GET /api/cases/{id}` (메일·이력·추출 상태 포함), 원문·첨부 다운로드 링크(`rawUrl`, `attachmentFiles[].url`). API 문서: `http://localhost:8000/docs`
- 이력(case_events) 종류: CASE_CREATED, PIPELINE_STARTED/RUN/FAILED, DRAFT_PREPARED, DRAFT_SAVED, MAIL_SENT, REPLY_MERGED — 각 수행자(actor)·시각·상세(detail JSON) 포함(NFR-05, FR-107).
- **발송 기록의 한계:** 사이드로드 환경에서는 보내기 순간을 잡을 수 없어, 담당자가 **보낸 편지함에서 그 메일을 LEONA 패널로 열 때** 자동 기록됩니다(발송 시각은 원문 Date 헤더). 열지 않으면 `MAIL_SENT`가 빠질 수 있습니다 → 검수 시나리오에 "보낸 메일 한 번 열기"를 넣어 주세요.

## 2026-10-02 B·C트랙 병합 결과 (현재 구현 기준)

- 새 B트랙의 DB 컬럼 14개와 첨부 표·선사 추출을 유지했다. 이번 병합에서 DB 컬럼·공통 입력 필드는 추가하지 않았다.
- 견적은 `rates` DB만 조회한다. 제공 `샘플_요율표.xlsx`는 기존 `/api/rates/import`로 등록하며, `SAMPLE_RATE_WORKBOOK` 직접 조회 설정은 제거했다. 실제 앱 DB에 제공 요율 35건을 등록했다.
- 선사·보험·일정·Free Time·원본 근거 컬럼이 요율 내보내기/재가져오기에서도 보존된다. 외부 자료·새 라이브러리는 추가하지 않았다.
